Microservices Playground — Design Document

Individual project · experiments-lab (github.com/drm0011/experiments-lab) · Version 1.0 · Last updated: 2026-11-22

1. Context and purpose

The individual project complements the semester group project (Automated Impacted Test Case Selection and Execution in GitLab CI/CD for Thermo Fisher's Velox application). Where the group project consumes a single CI/CD pipeline, the individual project investigates how to design, secure, and operate CI/CD for a microservices architecture — and, per coach feedback, uses it to prove the complex-enterprise learning outcomes (LO1: distributed data, communication patterns, security by design) that the group project cannot.

Research question (LO3 track, complete): How is a CI/CD pipeline for a microservices application — covering DevSecOps practice — designed so that it is fast, reliable, and safe to trust?

The system under investigation is the tiny shop (catalog, inventory, orders + React frontend), deliberately small so that every mechanism is understandable, with failure modes designed in so reliability is observable. A planned evolution reworks it into a banking system to deepen the LO1 track (see §10).

4. Communication patterns

  • Synchronous request/response — browser → each API (direct, CORS-open); orders → inventory (GET /stock/{id}) is the single service-to-service call, made through IHttpClientFactory.
  • Cluster DNS — in Kubernetes, the same call uses http://inventory:8080 resolved by CoreDNS to the Service, surviving pod replacement.
  • Contracts — the orders→inventory dependency is made explicit as committed OpenAPI snapshots with a CI drift gate; a contract change triggers the dependent service's pipeline (closing the path-filter blind spot).
  • Asynchronous messaging — deliberately absent today. This is the primary gap the banking evolution addresses (RabbitMQ AccountClosed events), per the coach's "deleted account" scenario.

5. Data flows

Order placement (happy path)

Shop User → frontend → POST /orders {itemId, quantity}
                        → orders → GET inventory /stock/{itemId}
                        → stock sufficient → order accepted (200), listed

Failure flows (designed in)

stock == 0        → 409 "insufficient stock"
inventory down    → 503 "inventory unavailable"   (try/catch on the HTTP call)

Contract flow

inventory /openapi/v1.json  → committed contracts/inventory-openapi.json
script regenerates + diffs → drift fails CI (contracts.yml)
contract change            → triggers orders pipeline (dependent consumer)

6. Delivery and operations

  1. Per-service pipelines — one workflow per service, path-filtered; a change to orders builds only orders.
  2. Security gates — each pipeline: build → docker build → Trivy scan (fail on HIGH/CRITICAL) → publish to GHCR (sha-<commit> + latest); gitleaks scans full history on every push; least-privilege permissions: blocks.
  3. Deploy-smoke — on main, an ephemeral k3d cluster is created inside Actions, the manifests are applied (pulling from GHCR), and the failure modes are verified (200 → 409 → 503 → recovery) before teardown.
  4. Local cluster — the laptop k3d cluster pulls the same images from GHCR; manual kubectl apply/rollout restart is the release step (CI cannot reach the laptop; automating it would require a hosted cluster — a deliberate trade-off).

7. Reliability design and findings

  • Probes — readiness/liveness on /health connect app health to cluster behavior.
  • Self-healing — verified: pod deletion → brief 503 → automatic replacement (~2 s); scale --replicas=0/1 provides a controllable failure window for demos.
  • Finding: stale connection pool — after inventory recovers, the first order can still 503 because IHttpClientFactory pools the handler indefinitely and orders reuses a connection to the dead pod IP. Fix path: Polly AddStandardResilienceHandler (retry + pooled-connection lifetime). This finding is evidence-backed and validates the resilience backlog item.
  • Finding: kubectl wait race — kubectl wait --for=condition=Ready fails when zero pods match momentarily; replaced with kubectl rollout status.

8. Design decisions (ADR-style log)

D-01 — Microservices as the vehicle

Context: The group project is one pipeline. Decision: Build a small multi-service system so per-service builds, cross-service dependencies, and selective runs are forced to the surface. Consequence: More moving parts, but every CI/CD question becomes real and measurable.

D-02 — Designed-in failure modes

Decision: Make 409 (insufficient stock) and 503 (dependency down) first-class behaviors. Consequence: Reliability is observable and testable in demos and in CI smoke tests — mirroring the group project's conservative-fallback philosophy.

D-03 — Per-service pipelines with path filters

Decision: One workflow per service, triggered only by that service's files (plus its contracts). Consequence: Isolation and speed; the blind spot (behavioral dependencies invisible to paths) is mitigated by the contract gate (D-06).

D-04 — k3s via k3d, not systemd k3s/kind

Decision: Run a real k3s cluster inside Docker. Consequence: No sudo, disposable clusters, identical machinery reusable as an ephemeral cluster in CI (deploy-smoke).

D-05 — NodePort now, ingress later

Decision: Expose services via NodePort + k3d host mappings (browser demo works with existing localhost URLs); defer Traefik ingress. Consequence: Simplicity today; ingress remains backlog for production-style routing.

D-06 — Security gates: Trivy + gitleaks, fail on HIGH/CRITICAL

Decision: Only Trivy-passing images are published; gitleaks scans full history; residual findings go to a justified .trivyignore. Consequence: The gate caught real 2026 CVEs and a transitive dependency our own feature introduced — enforced security, not remembered security.

D-07 — Committed OpenAPI contracts with drift gate

Decision: Provider contracts committed; regeneration + diff fails CI; contract changes trigger dependent pipelines. Consequence: The orders→inventory dependency is explicit and reacted-to. Limitation: anonymous return types produce empty schemas — typed results are the next step.

D-08 — GHCR sha-tag + latest; ephemeral deploy-smoke

Decision: Publish immutable sha- and moving latest tags; validate every main push by deploying into a throwaway CI cluster. Consequence: The full delivery loop (build → scan → publish → deploy → verify) is automated; the persistent laptop cluster remains a manual release step by design.

D-09 — In-memory data only (for now)

Decision: No database in the shop. Consequence: State resets on restart (honest limitation); distributed data arrives with the banking evolution (Postgres per service, PVCs).

9. Known limitations and deliberate gaps

  • In-memory data — no persistence, no database-per-service yet
  • No asynchronous messaging (RabbitMQ planned in the banking evolution)
  • No authentication/authorization (security-by-design backlog item)
  • NodePort instead of ingress; latest tags in manifests (sha-tags exist but aren't wired to deploys)
  • Single-node cluster — no multi-node scheduling behavior
  • No image signing yet (Cosign backlog)
  • Frontend hardcodes localhost API URLs (build-time VITE_* config pending)

10. Roadmap — evolution into a banking system (LO1 track)

The shop is being reworked into a mini-bank to carry the LO1 evidence the coach's feedback demands: distributed data and communication patterns, concretely the deleted-account scenario (a debt letter must still be sent after the account is gone).

Shop (v1)Bank (v2)
catalogaccount-service — open/close accounts; publishes AccountClosed (Go)
inventoryledger-service — balances, idempotent postings (Go)
ordersnotify-service — debt letter from event-carried state (Go)
sync orders→inventorysync validation (insufficient funds → 409) plus RabbitMQ pub/sub for AccountClosed
shop UIbanking dashboard: accounts, event feed, DLQ inspector

Key design problems for v2: sync vs async boundaries, event-carried state transfer (the debt-letter insight), the outbox pattern (no lost events between DB and queue), idempotent consumers (no double postings), and dead-letter handling (no silently dropped messages). All delivery machinery from v1 (pipelines, gates, contracts, GHCR, deploy-smoke, k3s) carries over unchanged in spirit.
